# Живые обновления UI (WebSocket)

Не входит в текущий релиз. Черновик для обсуждения.

Сейчас веб и Android узнают об изменениях только если сами сходят в REST: фоновый SWR, прогрев кеша, опрос джобы импорта. Идея — **держать одно постоянное соединение** и получать с сервера сигнал «данные изменились», а CRUD оставить на `GET/POST /api/v1/...`.

Связанные документы: [ui-api-cache.md](../docs/ui-api-cache.md), [webhooks.md](webhooks.md), [android-client-platform.md](../docs/android-client-platform.md), [install/nginx.md](../docs/install/nginx.md), [team-collaboration.md](team-collaboration.md).

---

## Зачем

На вебе нет таймера «опрашивать всё каждую секунду», но поток GET всё равно плотный:

| Источник | Что происходит сейчас |
|----------|------------------------|
| SWR ref-cache (`web/src/lib/ref-cache.ts`) | Любой `GET` при попадании в кеш **сразу** запускает фоновый revalidate. Cooldown **нет** (на Android — 60 с + отложенный старт 3 с). |
| Прогрев после входа | `warmRefCache()` параллельно бьёт dashboard, `ui/meta`, счета (два варианта), бюджет, две страницы операций. |
| Страницы | `$effect` на `refCacheUpdate` снова вызывает `load()` → ещё GET → ещё revalidate. |
| После записи | `clearRefCache` и silent `load`/`loadAll` — полная перечитка экрана. |
| Импорт | `GET /import/jobs/{id}` каждые **1,2 с**, пока джоба жива. |
| Другой клиент / крон | Автосписание кредита, future→manual, подписка, правка с телефона: открытая вкладка веба **не узнает**, пока сама не сходит в сеть. |

Несколько вкладок, форм и справочников на одном экране умножают это. Отсюда ощущение «сервер засыпали GET». Серверный in-memory кеш (TTL 1–5 мин) лишь удешевляет ответ, запросы к процессу всё равно идут.

Канал обновлений решает две разные задачи:

1. **Убрать холостой шум** — не revalidate «на всякий случай».
2. **Увидеть чужие изменения сразу** — второй клиент, другая вкладка, фоновая джоба сервера.

## Чего не делать

- **Не переносить CRUD на сокеты.** Создание операции, фильтры, пагинация, экспорт, OpenAPI-клиенты остаются HTTP. Сокет — сигнал, не замена API.
- **Не пушить по сокету полные снимки** дашборда и списков. Дублирование REST, версионирование пейлоадов, расхождение с [точечным обновлением UI](android-incremental-ui-updates.md).
- **Не делать Android зависимым от живого канала.** Фон убивает соединение; офлайн, outbox, `GET /sync/transaction-changes` остаются источником правды на мобильном.
- **Не вводить второй «источник истины» рядом с SQLite.** Событие = «сходи за свежим REST» или «патчни id из уже существующей ленты», не отдельная реплика данных в браузере.

## Транспорт: WebSocket vs SSE vs «ещё poll»

Целевой транспорт — **WebSocket** (как в постановке: веб на постоянном канале). Контракт сообщений держать JSON-текстом, чтобы при необходимости подставить SSE тем же телом.

| | WebSocket | SSE (`text/event-stream`) | Частый GET / long-poll |
|---|-----------|---------------------------|-------------------------|
| Направление | двусторонний | только сервер → клиент | клиент тянет |
| Прокси | `Upgrade` + таймаут простоя | `proxy_buffering off` | уже работает |
| Переподключение | свой backoff | `EventSource` сам | свой |
| Импорт / подписка на экран | клиент шлёт `subscribe` | только REST + один поток | poll |
| Нагрузка на SQLite | нет (события из памяти) | нет | да, даже при cache hit |

**Почему не сразу SSE.** Для инвалидации хватило бы и SSE, но нужны: прогресс импорта, подписка на текущий экран, единый канал web+Android (foreground), явный ping. Это проще на сокете. Если на этапе прототипа reverse proxy окажется больным местом — тот же JSON уходит в SSE, клиентский разбор не ломается.

**Почему не long-poll.** Это тот же шторм запросов в более вежливой форме; для self-hosted с nginx проще один Upgrade.

Библиотека на сервере — на этапе реализации (стандартный `gorilla/websocket` или `coder/websocket`). В `go.mod` сейчас сокетов нет.

## Архитектура

```
  [браузер / Android foreground]
           │  WebSocket
           ▼
  GET /api/v1/realtime  (Upgrade)
           │
           ▼
  in-memory Hub (по user_id)
           ▲
           │ Publish после мутации / джобы
  REST handlers, import job, scheduler
           │
           ▼
  SQLite + InvalidateUser (apicache) как сейчас
```

REST остаётся единственным способом **изменить** учёт. Сокет только доставляет факт изменения тем сессиям пользователя, которые сейчас онлайн.

### Эндпоинт

- `GET /api/v1/realtime` — handshake WebSocket.
- Та же авторизация, что у API: session cookie (веб, same-origin) или `Authorization: Bearer` (Android / внешний клиент). Токен **не** класть в query (`?token=`) — попадёт в access-логи nginx.
- Origin / Host сверять с `BUHGALTER_ALLOWED_HOSTS` и внешним URL из админки (CSRF на Upgrade).
- Не кешировать: добавить путь в исключения [apicache](../docs/ui-api-cache.md) рядом с `/health` и `/sync/transaction-changes`.

### Хаб

Новый пакет `server/internal/realtime`:

- одна кучка соединений на `user_id`;
- `Publish(userID, Event)` — неблокирующая (буфер на соединение, медленный клиент отключается);
- лимит соединений на пользователя (вкладки: 8–16, лишнее — закрыть самое старое);
- ping сервера каждые ~25 с (иначе nginx по умолчанию рвёт простой за 60 с);
- процесс один, SQLite один: **in-memory достаточно**. Несколько реплик приложения без sticky/pubsub и так не живут на SQLite; при [PostgreSQL](postgresql.md) позже — `LISTEN/NOTIFY` или NATS, не сейчас.

Точка публикации — та же, что уже сбрасывает GET-кеш: middleware мутаций (`POST/PUT/PATCH/DELETE`) + завершение import job + фоновые джобы (автосписание, активация future, подписки, периодические, автопополнение). Сейчас `InvalidateUser` после HTTP-записи есть; **фоновые джобы должны звать тот же хук** (`InvalidateUser` + `Publish`), иначе вкладка не узнает про списание кредита, пока не обновит страницу.

### Контракт событий (черновик)

Версия в поле `v`. Клиент неизвестный `type` игнорирует.

```json
{
  "v": 1,
  "type": "invalidate",
  "at": "2026-09-18T12:00:00Z",
  "entities": ["transaction", "account"],
  "ids": ["…"],
  "hint_paths": ["/api/v1/dashboard", "/api/v1/accounts"]
}
```

| `type` | Когда | Клиент |
|--------|--------|--------|
| `hello` | после handshake | курсор ленты, лимит ping |
| `ping` / `pong` | keepalive | ответить или игнорировать, если native ping |
| `invalidate` | учёт изменился | сбросить затронутый ref-cache, **перечитать только открытый экран** |
| `import.progress` | джоба импорта | обновить UI, **перестать poll** `GET /import/jobs/{id}` |
| `import.done` / `import.failed` | финал джобы | как сейчас после poll, плюс invalidate ledger |
| `session.revoked` | logout / смена пароля / блокировка | закрыть сокет, сценарий session expired |

MVP можно упростить до одного грубого `invalidate` без `hint_paths`: открытая страница одна, лишний GET по её путям дешевле нынешнего прогрева всего кеша. Тонкие `entities`/`ids` — вторая очередь, стыкуется с уже существующей лентой `user_change_events`.

Клиент → сервер (опционально, не в первом срезе):

```json
{ "v": 1, "type": "subscribe", "paths": ["/api/v1/dashboard"] }
```

Без подписки сервер шлёт все события пользователя — для 1–2 вкладок это нормально.

## Поведение веба

1. После успешного `loadUser()` открыть сокет (рядом с `warmRefCache()`).
2. Пока сокет жив и вкладка видима (`document.visibilityState === 'visible'`):
   - **не** запускать фоновый SWR-revalidate на каждый GET;
   - после **своей** мутации по-прежнему silent `load` текущего экрана (не ждать эхо-события; эхо можно дедуплицировать по `request_id`, если добавим).
3. По событию `invalidate` — `refCacheUpdate` только для путей открытой страницы (уже есть path-aware watch). Не вызывать `warmRefCache` целиком.
4. Вкладка в фоне: сокет можно оставить (пинг дешёвый) или приостановить; при `visibilitychange` → visible — один refetch экрана + сверка курсора.
5. Обрыв: backoff 1s → 2s → … → 30s; после reconnect — текущий экран + `GET /sync/transaction-changes` (веб сегодня ленту почти не использует — имеет смысл **тот же catch-up**, что Android).
6. Нет сокета (прокси режет Upgrade, старый сервер): **тихо откатиться** на SWR с cooldown, как сейчас Android. Веб не должен «стоять» без обновлений.

Импорт: подписка на `import.*` вместо цикла `sleep(1200)`. REST `GET /import/jobs/{id}` оставить для догона после reload страницы.

## Android

Для телефона это **нормально как дополнение**, не как замена текущей модели. Android уже спокойнее веба: SWR cooldown 60 с, warm не чаще 5 мин, лента `GET /sync/transaction-changes`, probe `/health` раз в 180 с, виджеты — WorkManager раз в час. Сокет ему нужен меньше, чем открытой вкладке.

Не блокирует веб-MVP (этап 4). **Нельзя** сделать учёт на телефоне зависимым от живого канала.

| Состояние | Канал |
|-----------|--------|
| Приложение на экране, сеть есть | сокет имеет смысл: правка с веба / автосписание видны сразу, без ждать cooldown |
| Ушёл в фон / Doze / MIUI «закрыть все» | сокет **не держать**. WebView замораживают; на Xiaomi renderer уже уводят в SmartPower. Догон на resume: probe + warm + `transaction-changes` — как сейчас |
| Офлайн | outbox + ref-cache; сокет не открывать |
| Виджеты | снимок + `WidgetRefreshWorker` (OkHttp). Сокет виджету не поможет, пока процесс мёртв |

### Почему не «тот же JS WebSocket, что в браузере»

WebView сидит на `https://localhost`. REST уже не идёт «голым» `fetch`:

- LAN `http://192.168.x.x` — CapacitorHttp / mixed content;
- внешний HTTPS с самоподписанным сертификатом — native `SslTrust` (OkHttp), не сертификаты Chromium.

`new WebSocket(...)` из JS **этот путь не использует**. На LAN `ws://` скорее всего упрётся в mixed content; на `wss://` с TOFU — в недоверенный сертификат. Рабочий вариант для Android — **native WebSocket на OkHttp** в том же духе, что `SslTrust.request` (отдельный Capacitor plugin или расширение `SslTrust`), плюс Bearer как у API. JS-сокет в WebView — только если origin и сертификат и так доверяются Chromium (почти никогда в self-hosted).

Пока native-канала нет — Android остаётся на REST. Это не регресс: cooldown и лента изменений уже закрывают фон и догон. Сокет на телефоне — про «открыл приложение, а на вебе только что провели операцию».

## Что переиспользовать

| Уже есть | Роль в живом канале |
|----------|---------------------|
| `user_change_events` + `GET /sync/transaction-changes` | догон после обрыва; позже — расширить триггеры за пределы `transactions` (счета, долги, кредиты, бюджеты) |
| `apicache` middleware | хук `Publish` рядом с инвалидацией GET |
| `refCacheUpdate` / `assignIfChanged` | UI уже умеет мягко патчить экран без спиннера |
| [webhooks.md](webhooks.md) | **та же шина событий**, другой транспорт (HTTP POST наружу). Имена вроде `transaction.created` лучше сразу совпасть |
| [team-collaboration.md](team-collaboration.md) | когда появятся общие счета, хаб шлёт всем членам household, не только автору мутации |

Ленту изменений расширять не обязательно для MVP: грубый `invalidate` + refetch экрана закрывает веб. Расширение `user_change_events` — когда Android/веб начнут патчить списки по id без полного GET.

## Прокси и деплой

Дополнить [install/nginx.md](../docs/install/nginx.md) и `docker/nginx.conf.example`:

```nginx
location /api/v1/realtime {
    proxy_pass http://127.0.0.1:8765;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 3600s;
}
```

Caddy обычно проксирует Upgrade сам; Cloudflare — WebSocket включён на плане, idle короче, ping обязателен. Без этих заголовков клиент обязан уйти на SWR-fallback.

## Нагрузка и безопасность

- Self-hosted, мало пользователей: сотни простых ping в минуту дешевле сотен GET дашборда в секунду.
- События **только** своему `user_id` (тест как у `transaction/changes`: чужой пользователь не видит ленту).
- Не слать в сокет токены, пароли, полные выгрузки.
- Rate limit: новых handshake с IP / с пользователя.
- Админские события (`admin/users`) — только в сокеты админов, не в комнату обычного user.
- SQLite writer lock сокет не трогает: публикация после уже совершённой записи.

## Этапы

Нумерация — порядок работ, не номер релиза.

### 0. Дёшево без сокетов (можно сразу, даже если канал отложат)

Имеет смысл **сделать до** WebSocket: часто этого хватает против «сотен GET».

- [ ] Cooldown фонового SWR на вебе, как на Android (`REVALIDATE_COOLDOWN_MS` 60 с, отложенный старт).
- [ ] Не revalidate скрытую вкладку (`document.hidden`).
- [ ] Свести дубли `load()` после записи (один refetch экрана, не N эффектов).
- [ ] Замерить: access-лог / Network при открытой главной, после сохранения операции, две вкладки. Зафиксировать «было / стало» в release notes, когда дойдут руки.

### 1. Шина на сервере

- [ ] Пакет `realtime`: Hub, `Publish`, лимит соединений, ping.
- [ ] Хук из apicache-middleware (успешная мутация) и из import job / scheduler.
- [ ] Юнит-тесты хаба: два клиента одного user, изоляция чужого user, медленный клиент.

### 2. WebSocket + веб

- [ ] `GET /api/v1/realtime`, OpenAPI (описание handshake; WS в OpenAPI ограничен — текстом).
- [ ] Клиент `web/src/lib/realtime.ts`: connect, backoff, fallback на SWR.
- [ ] Событие `invalidate` → refetch открытой страницы; при живом сокете выключить «revalidate на каждый GET».
- [ ] Документация nginx.
- [ ] E2E: две вкладки (или два контекста Playwright) — операция в одной, баланс во второй без ручного reload.

### 3. Импорт и догон

- [ ] `import.progress` / `done` / `failed` вместо poll 1,2 с.
- [ ] После reconnect — `GET /sync/transaction-changes` и на вебе.

### 4. Тонкая инвалидация и Android

- [ ] `hint_paths` / `entities` + path-aware `refCacheUpdate` без полного `load()`.
- [ ] Расширить `user_change_events` за операции (если патч списков по id нужен и на вебе).
- [ ] Android **foreground**: native OkHttp WebSocket (SslTrust / тот же TOFU, что REST), не `new WebSocket` из WebView.
- [ ] Фон, виджеты, офлайн — без сокета; resume по-прежнему probe + `transaction-changes`.

## Критерии приёмки (когда возьмём в релиз)

- [ ] Открытая главная при живом сокете **не** долбит `GET /dashboard` в фоне без события и без своего действия пользователя.
- [ ] Операция, созданная во второй вкладке (или в Android), появляется на первой без F5; спойлеры и скролл не сбрасываются ([android-incremental-ui-updates.md](android-incremental-ui-updates.md)).
- [ ] Автосписание / future на сервере обновляет открытый веб.
- [ ] Импорт показывает прогресс без цикла GET каждые 1,2 с.
- [ ] Прокси без `Upgrade`: UI живой, режим как сегодня (SWR), без вечной «Загрузка…».
- [ ] Обрыв сети → reconnect → нет дыр в списке операций (догон лентой или refetch).
- [ ] Чужой пользователь не получает чужие события (интеграционный тест).

## Открытые вопросы

- [ ] Брать WebSocket сразу или прототип на SSE (тот же JSON), если nginx у типичного деплоя без Upgrade надолго?
- [ ] Грубый `invalidate` на все сущности пользователя vs сразу `hint_paths`?
- [ ] Склеивать ли шину с [webhooks.md](webhooks.md) в одном пакете `internal/events` или два независимых publisher?
- [ ] Нужен ли `request_id` на мутации, чтобы автор не refetch дважды (свой silent load + эхо сокета)?
- [ ] Админка (очередь сброса пароля, диагностика) — тот же сокет или редкий poll оставить?
- [ ] Лимит вкладок и поведение при превышении — закрывать старое или отказывать новым?
