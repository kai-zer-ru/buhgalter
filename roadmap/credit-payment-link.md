# Привязка операции к оплате кредита

**Реализовано** в **v1.6.0** ([ROADMAP](../ROADMAP.md#v160)). Аналог привязки к [подпискам](../docs/subscriptions.md): обычный расход можно сделать платежом по кредиту, а при создании — выбрать кредит прямо в форме операции.

Связанные документы: [ui-credits.md](../docs/ui-credits.md), [categories-and-icons.md](../docs/categories-and-icons.md), [transactions-display.md](../docs/transactions-display.md).

---

## Зачем

Сейчас платёж по кредиту создаётся только с карточки кредита («Оплатить» / автосписание / ретро «Списан со счёта»). Если пользователь уже завёл обычный расход (импорт, перехват уведомления, ручной ввод) — связать его с графиком нельзя: либо дубль, либо платёж «мимо» учёта.

| Сейчас | Нужно |
|--------|--------|
| Оплата только с `/credits/{id}` | Расход из журнала / формы → платёж по графику |
| Категория «Кредиты» в форме операции недоступна (`is_system`) | В форме расхода «Кредиты» выбирается; вместо подкатегорий — список активных кредитов |
| `credit_payment_linked` только у операций, созданных движком кредита | Та же связь у уже существующих операций после привязки |
| Старые платежи по графику могут быть не в «Кредиты» | Автобэкфилл: связанные с `credit_payments` операции → системная «Кредиты» |

---

## Scope (v1.6.0)

| Возможность | Суть |
|-------------|------|
| Категория «Кредиты» в форме | Расход: системная «Кредиты» в picker категорий (исключение из фильтра `!is_system`) |
| Вместо подкатегорий — кредиты | При выбранной «Кредиты» второй уровень — активные кредиты (`status=active`), не `subcategories` |
| Создание = оплата | Сохранение формы с выбранным кредитом применяет ближайший неоплаченный `scheduled` (как `POST /credits/{id}/payments`) |
| Привязка существующей | В журнале: «Сделать платежом по кредиту» / выбор кредита → та же семантика оплаты с переиспользованием операции |
| Категория после привязки | У операции: `category_id` = «Кредиты», описание по имени кредита (если пустое), `credit_payment_linked=true` |
| Автобэкфилл категории | Уже связанные с графиком операции без «Кредиты» — без UI, при старте/миграции переносятся в системную категорию |
| Web + Android | Одинаковые сценарии; Android — online-only для attach/create-as-payment (как find/attach подписок) |

## Модель (без новых сущностей)

Связь уже есть: `credit_payments.transaction_id` → флаг `credit_payment_linked` на операции. Новых колонок на `transactions` не требуется.

Поведение привязки совпадает с текущей оплатой:

1. Цель — **ближайший** неоплаченный `scheduled` (как сейчас в UI/API).
2. Сумма — из операции (или поля формы); не больше остатка кредита; строка графика обновляется суммой платежа.
3. Счёт — из операции; `debit_account_id` кредита не меняется.
4. Дата — из операции; если в будущем — `kind=future`, как у обычной оплаты.
5. После связи операция **не** редактируется через `PUT /transactions/{id}` (уже так).
6. «Удалить платёж» на графике — как сейчас: платёж снова `scheduled`, связанная операция удаляется.

**Подкатегории.** В отличие от подписок, ленивые подкатегории по имени кредита **не вводим** в этом пункте: второй уровень в форме — UI-список кредитов, в БД у операции `subcategory_id` остаётся `null` (как у текущих платежей с карточки). Имя кредита — в `description`.

### Автобэкфилл категории у старых платежей

Операции, уже связанные с графиком (`credit_payments.transaction_id IS NOT NULL`), всегда должны быть в системной «Кредиты». На практике часть могла остаться в другой категории (ранние версии, импорт, ручная правка до блокировки `PUT`).

Поведение (сервер, без отдельного экрана):

1. Критерий: есть строка `credit_payments` с этим `transaction_id`.
2. Расход → `category_id` = системная expense «Кредиты»; доход (выдача / `principal_affects_balance`) → income «Кредиты».
3. `subcategory_id` сбрасывается в `null` (системные подкатегории у «Кредиты» не используются).
4. Сумма, дата, счёт, описание, `affects_balance` **не** трогаем.
5. Идемпотентно: повторный прогон no-op, если категория уже верная.
6. Запуск: ensure при старте (рядом с `categoryseed` / credit startup) или одноразовая goose-миграция + ensure на всякий случай.

Это **не** автопоиск «похожих» расходов без связи с графиком и не score-кандидаты как у подписок — только выравнивание категории у уже привязанных платежей.

## Сценарии UI

### 1. Создать расход как платёж

1. Форма новой операции (web / Android), тип расход.
2. Категория **«Кредиты»** (системная, только expense; income «Кредиты» в форме не предлагать).
3. Вместо списка подкатегорий — активные кредиты (имя; опционально ближайшая сумма/дата платежа как подпись).
4. Обязателен выбор кредита. Пустой список → подсказка «Нет активных кредитов» + ссылка в `/credits`.
5. Сохранение → оплата ближайшего `scheduled` с полями формы (сумма, счёт, дата, описание).
6. Успех → журнал / карточка кредита (как после «Оплатить»).

Префилл суммы/даты из ближайшего платежа при выборе кредита — желательно (как в модалке «Оплата»), но не блокирует ручной ввод.

### 2. Сделать уже созданную операцию платежом

Доступно для **расхода**, у которого ещё нет `credit_payment_linked` и нет `subscription_id` (и не нога перевода/комиссии).

| Место | Действие |
|-------|----------|
| Журнал / главная / карточка счёта | Меню строки: «Сделать платежом по кредиту» |
| После выбора | Список активных кредитов (модалка / экран) → подтверждение |

После привязки:

- операция переносится в категорию «Кредиты»;
- связывается с ближайшим `scheduled`;
- пункт «Изменить» в журнале скрывается (`canEditTransaction`).

Отвязка отдельным действием **не** делается: только «Удалить платёж» на графике кредита (как сейчас).

### 3. Карточка кредита

Существующие «Оплатить» / автосписание / ретро **не меняются**. Новый путь — дополнительный вход в ту же доменную операцию.

## API (эскиз)

Предпочтительно расширить оплату, а не дублировать логику:

| Метод | Назначение |
|-------|------------|
| `POST /credits/{id}/payments` | Как сейчас; опционально `transaction_id` — переиспользовать существующий расход вместо `InsertTransaction` |
| `GET /credits?status=active` | Уже есть — источник списка для второго уровня формы |

Правила для `transaction_id`:

- операция пользователя, `type=expense`, не перевод/комиссия;
- ещё не связана с платежом кредита и не с подпиской;
- после успеха: категория «Кредиты», `credit_payments.transaction_id` = id, при необходимости правка суммы/даты/счёта/описания как при обычной оплате.

Создание «с нуля» из формы:

- либо клиент вызывает `POST /credits/{id}/payments` без `transaction_id` (создаёт операцию движок кредита);
- либо `POST /transactions` с полем `credit_id` → сервер внутри делает ту же оплату.

В OpenAPI зафиксировать один канонический путь; второй не плодить без нужды.

Ошибки (ключи в духе существующих credit-ошибок): нет pending `scheduled`, кредит закрыт, операция уже связана, сумма/тип невалидны.

## Отличие от подписок

| | Подписки | Кредиты (этот пункт) |
|--|----------|----------------------|
| Связь | `transactions.subscription_id` | `credit_payments.transaction_id` |
| Подкатегория | Lazy по имени подписки | Нет (`null`) |
| Второй уровень в форме | Пока нет (системные категории скрыты) | Список **кредитов** |
| Эффект привязки | Смена категории/подкатегории + id | Применение строки графика + смена категории |
| Поиск кандидатов | Score + `candidate-transactions` | В v1.6.0 **не** делаем: ручной выбор кредита из операции |

Экран «найти операции с кредита» (как `/subscriptions/{id}/find-transactions`) — **вне scope**; при необходимости — follow-up.

---

## Не входит

- Привязка к произвольной (не ближайшей) строке графика
- Привязка перевода / комиссии (доход по выдаче кредита — только в автобэкфилле категории, не через форму «сделать платежом»)
- Ленивые подкатегории «Кредиты» → имя кредита
- Автопоиск и привязка к графику расходов «на глаз» (score / find-transactions)
- Фоновая автопривязка из банка / перехвата уведомлений
- Изменение правил редактирования уже связанных операций
- То же UX для категории «Подписки» в форме создания (отдельная задача)

## Чеклист реализации

1. API: оплата с опциональным `transaction_id` (+ тесты: happy path, уже связана, нет pending).
2. Ensure/миграция: связанные с `credit_payments` операции → категория «Кредиты» (expense/income по типу); тест на идемпотентность.
3. Web `TransactionForm`: показать «Кредиты»; при выборе — список кредитов вместо subcategories; submit → pay/attach.
4. Android: тот же UX; attach/create-as-payment — `requireOnline()`.
5. Меню операции: «Сделать платежом по кредиту» рядом с «Сделать подпиской».
6. i18n web + Android + `server/ui_locales`.
7. Обновить [ui-credits.md](../docs/ui-credits.md), [transactions-display.md](../docs/transactions-display.md), OpenAPI; после релиза — краткая ссылка из [categories-and-icons.md](../docs/categories-and-icons.md).

## Открытые вопросы

- [ ] При привязке существующей операции с суммой ≠ ближайшему платежу: всегда перезаписывать сумму строки графика (как ручная оплата) или отклонять при большом расхождении?
  - **Решение:** всегда перезаписывать (как ручная оплата).
- [ ] Нужен ли пресет суммы/даты из графика при выборе кредита в форме, или достаточно ручного ввода?
  - **Решение:** префилл из `next_payment_*` / `monthly_payment` и `debit_account_id` при выборе кредита; ручной ввод остаётся.
