# Включение / отключение функционала в админке

**Реализовано** в **v1.5.0** — актуальная документация: [docs/feature-toggles.md](../docs/feature-toggles.md). Ниже — исходный план.

Администратор инстанса включает и выключает **опциональные модули** продукта. Цель — упростить UI/API на self-hosted установке («мне не нужны кредиты») и зафиксировать правило: **каждый новый опциональный функционал сразу получает флаг и может быть отключён**.

Сюда же переезжает нынешний `system_settings.registration_enabled` ([user-status.md](../docs/api/user-status.md)): один каталог флагов вместо отдельного поля в settings.

---

## Зачем

- На одном сервере часто один-два пользователя; лишние разделы (кредиты, бюджет, подписки) только шумят в навигации.
- Часть модулей тянет фон (автосписание, уведомления) — выключение должно останавливать и это.
- Без единого механизма каждый новый экран «просто появляется» у всех; откатить нельзя без правки кода.

---

## Решения

| Тема | Решение |
|------|---------|
| Уровень | **Инстанс** (админ), не per-user. Все пользователи видят один и тот же набор модулей. |
| Кто меняет | Только `is_admin` через админку (раздел системных настроек). |
| Данные при выключении | **Не удалять.** История, справочники, расписания остаются в БД; после включения доступ возвращается. |
| Ядро | Счета, категории, базовые операции (доход/расход/перевод), auth, админка, профиль — **нельзя отключить**. |
| Клиенты | Web и Android читают один снимок флагов и прячут навигацию/роуты одинаково. |
| Новый функционал | Опциональный модуль **не мержится** без ключа флага, гейтов API/UI и строки в каталоге ниже. |

Пользовательские toggle каналов/триггеров ([notifications.md](../docs/notifications.md)) остаются **внутри** модуля: они работают только если инстанс-флаг `notifications` включён.

## Модель

### Каталог в коде + overrides в БД

- В коде — **реестр** известных флагов: `key`, человекочитаемые title/description (i18n), `default_enabled`.
- В БД — таблица overrides, например `feature_flags (key TEXT PRIMARY KEY, enabled INTEGER NOT NULL, updated_at …)`.
- Нет строки в БД → берётся `default_enabled` из реестра.
- Неизвестный ключ в PUT от клиента → ошибка валидации (не молча игнорировать).
- Ключ из БД, которого уже нет в реестре (после отката версии) → игнорировать при чтении, не падать.

Миграция при появлении нового флага: `INSERT OR IGNORE` со стартовым значением (обычно `1`, чтобы не ломать существующие установки). Альтернатива без INSERT — только default в коде; INSERT предпочтительнее для явного снимка в SQL.

Не плодить колонку в `system_settings` на каждый модуль — реестр+таблица масштабируется без раздувания settings API.

### Ключи

Стабильные snake_case идентификаторы, не менять после релиза:

| Ключ | Модуль | Default |
|------|--------|---------|
| `registration` | Самостоятельная регистрация пользователей | `false` (как сейчас у `registration_enabled`) |
| `debts` | Долги | `true` |
| `credits` | Кредиты (вкл. ипотеку) | `true` |
| `budget` | Бюджет | `true` |
| `subscriptions` | Подписки | `true` |
| `recurring` | Периодические операции | `true` |
| `balance_maintenance` | Автопополнение счёта | `true` |
| `import_export` | Импорт / экспорт | `true` |
| `stats` | Статистика `/stats` | `true` |
| `notifications` | Уведомления (Telegram / MAX, настройки, исходящая доставка) | `true` |
| `merchants_tags` | Магазины и теги | `true` (когда модуль появится) |
| `transaction_templates` | Шаблоны операций | `true` (когда модуль появится) |
| `receipt_scanner` | Сканер чеков | `true` (когда модуль появится) |
| `savings_goals` | Цели накопления | `true` (когда модуль появится) |

Кредитные карты — **тип счёта**, не отдельный модуль в MVP: отключать через флаги не предлагаем (иначе ломается модель счетов).

**Миграция `registration`:** скопировать текущее `system_settings.registration_enabled` в `feature_flags`; колонку из `system_settings` и поле из `GET/PUT /admin/settings` убрать (breaking для API-клиентов админки — отметить в release notes). Setup (`POST /setup`) и админский toggle пишут в `feature_flags`, не в settings. Поведение без изменений: `POST /auth/register` при выключенном флаге — отказ; ссылка регистрации на `/login` скрыта; шаблон/триггер `user_registration` в UI уведомлений — только при `registration = true` (и при включённом `notifications`).

**Публичное чтение:** значение `registration` нужно **без** сессии (`GET /setup/status` или узкий публичный снимок) — страница логина. Остальные флаги — только авторизованным.

При `notifications = false`: скрыть `/settings/notifications` (web/Android); API настроек/каналов/шаблонов — `FEATURE_DISABLED`; **вся** исходящая доставка останавливается (в т.ч. админские `password_reset` / `user_registration`). Токены и шаблоны в БД сохраняются.

Будущие пункты ROADMAP (`savings_goals`, `webhooks`, `bank_sync`, `team`, …) при реализации добавляют строку в эту таблицу **в том же PR**, что и сам функционал.

### Зависимости (MVP — плоско)

В первой версии флаги **независимы**. Если позже понадобится «подписки требуют recurring» — описать явно в реестре (`requires: []`) и валидировать в PUT; до этого не усложнять.

## Поведение при `enabled = false`

| Слой | Поведение |
|------|----------|
| Навигация (web / Android) | Пункт меню, хаб, виджеты модуля скрыты. |
| Прямой URL / deep link | Редирект на `/` или экран «модуль отключён админом» (один общий empty-state); без 500. |
| API модуля | `404` с кодом вроде `FEATURE_DISABLED` (или `403` — выбрать один и зафиксировать в OpenAPI). Список/CRUD недоступны. |
| Связанные поля в «чужих» ответах | Опциональные поля модуля (`merchant_id`, теги и т.п.) можно отдавать как `null`/пусто **или** резать на записи — зафиксировать per-модуль; минимум: нельзя **создавать/менять** через API выключенного модуля. |
| Фоновые задачи | Scheduler / notify / auto-topup для модуля **не выполняются**. |
| Кеш | Смена флагов сбрасывает серверный GET-кеш и клиентский ref-cache (как `PUT /admin/settings`). |

Включение обратно: UI и API снова доступны, данные на месте, отложенные jobs продолжают с актуального состояния (без «догоняющего» шторма — как при обычном рестарте scheduler).

## API (черновик)

| Метод | Путь | Кто | Суть |
|-------|------|-----|------|
| `GET` | `/api/v1/features` | любой авторизованный | Снимок `{ key: bool, … }` или список `{ key, enabled }` — для UI. Только ключи из реестра. |
| `GET` | `/api/v1/admin/features` | admin | То же + метаданные (title keys / descriptions) для формы. |
| `PUT` | `/api/v1/admin/features` | admin | Полная или частичная запись overrides; ответ — актуальный снимок. |

Альтернатива поменьше: расширить `GET/PUT /admin/settings` объектом `features` и дублировать read-only снимок в `GET /auth/me`. Допустимо, если не раздувать `me`; отдельный `GET /features` предпочтительнее для кеша и явного контракта клиентов.

OpenAPI: русские `description`, схема ошибки `FEATURE_DISABLED`, примеры. После правок — `make copy-openapi`.

## UI

### Админка

- Блок **«Функционал»** / **«Модули»** на странице системных настроек (`/admin` или `/admin/system` — куда уедут настройки к моменту реализации).
- Таблица: название · краткое описание · `ToggleSwitch` (включая регистрацию — убрать отдельный toggle из текущих системных настроек).
- Сохранение — явная кнопка «Сохранить» (не автосейв каждого toggle), состояние после ответа API.
- Предупреждение при выключении модуля: данные сохранятся, раздел исчезнет у всех пользователей; фон модуля остановится. Для `registration` — короче: «новые пользователи не смогут зарегистрироваться сами».

### Клиенты

- После логина / при старте — загрузить флаги; хранить рядом с сессией (ref-cache с инвалидацией при мутации admin features).
- Хелпер `isFeatureEnabled('budget')` — единственная точка проверки в web и Android UI.
- Не дублировать списки пунктов меню вручную без проверки флага.

## Процесс: каждый новый опциональный функционал

Это **постоянное правило** разработки, не только задача v1.5.0.

### Когда нужен флаг

| Тип изменения | Флаг |
|---------------|------|
| Новый раздел / сущность / фоновый pipeline, которым можно не пользоваться | **Обязателен** |
| Расширение ядра (поля операции, багфикс, UX счетов/категорий) | Не нужен |
| Подфича внутри уже отключаемого модуля (например rollover бюджета) | Отдельный флаг **не** плодить; живёт под флагом модуля |
| Setup / смена пароля / ядро auth (кроме самостоятельной регистрации) | Не модуль продукта |

Если неочевидно — считать опциональным и добавить флаг (дешевле, чем вырезать потом).

### Чеклист в PR с новым модулем

1. Добавить ключ в **реестр** + i18n title/description.
2. Миграция: `INSERT OR IGNORE` default (обычно enabled).
3. Строка в каталоге этого документа (и после реализации — в `docs/`, когда документ переедет).
4. **API:** middleware или проверка в handler’ах модуля → `FEATURE_DISABLED`, если выключено.
5. **Scheduler / notify / workers** модуля — early-return при выключенном флаге.
6. **Web:** пункт навигации, роуты, виджеты — через `isFeatureEnabled`.
7. **Android:** то же (drawer, хабы, offline wrappers не должны слать мутации выключенного модуля).
8. **Тесты:** флаг off → API 404/код ошибки; UI не показывает пункт (unit/integration по принятому в модуле уровню).
9. ROADMAP / release notes: упомянуть, что модуль отключаемый в админке.

Ревьюер или автор не принимают модуль без пунктов 1–7.

### Связь с другими планами

В черновиках `roadmap/*.md` для опциональных модулей добавлять строку в Scope, например:

> Feature flag: `merchants_tags` (см. [feature-toggles.md](feature-toggles.md)).

Уже заведённые планы (магазины/теги, сканер чеков, цели, webhooks, …) при реализации обязаны пройти чеклист выше.

## Scope (v1.5.0)

| Возможность | Суть |
|-------------|------|
| Хранение | Таблица overrides + реестр в коде |
| Админка | Toggle’ы модулей из начального каталога (то, что уже есть в продукте) |
| `GET /features` (или эквивалент) | Снимок для web/Android |
| Гейты | API + nav + scheduler для модулей из каталога |
| Документ процесса | Чеклист «новый модуль → флаг» (этот файл) |
| Регистрация | Перенос `registration_enabled` → флаг `registration` + миграция значения |

На старте покрыть уже существующие разделы (`registration`, `debts`, `credits`, `budget`, `subscriptions`, `recurring`, `balance_maintenance`, `import_export`, `stats`, `notifications`). Флаги для ещё не реализованных модулей — в PR этих модулей, не заранее пустые ключи без кода.

---

## Не входит

- Per-user или per-household набор модулей (это уже про [семью](team-collaboration.md) / роли).
- Удаление данных при выключении / «жёсткая очистка модуля».
- Feature flags для канареечных раскаток и A/B (self-hosted, один инстанс).
- Отключение типов операций внутри ядра (например «запретить переводы»).

---

## Критерии приёмки

- [ ] Админ выключает модуль → пункт пропадает в web и Android у всех пользователей после обновления снимка флагов.
- [ ] API модуля отвечает ошибкой с стабильным кодом; прямые URL не падают.
- [ ] Фоновые задачи модуля не выполняются, пока флаг выключен.
- [ ] Включение восстанавливает доступ к прежним данным.
- [ ] `registration` читается из флагов; значение с существующих установок сохранено; `registration_enabled` убран из `system_settings` / admin settings API.
- [ ] В документации/чеклисте зафиксирован процесс для следующих модулей; хотя бы один существующий модуль полностью проведён как эталон (например `budget` или `subscriptions`).

---

## Открытые вопросы

- [ ] Точный HTTP-статус при выключенном модуле: `404` vs `403` (предложение: **404** + `FEATURE_DISABLED`, чтобы не светить наличие ресурса лишний раз — на self-hosted вторично, важнее единообразие с «нет такого раздела»).
- [ ] Нужен ли read-only режим «данные видно в операциях, раздела нет» для сущностей, встроенных в ленту (теги на операции) — решать per-модуль при реализации.
