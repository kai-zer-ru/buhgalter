# Подписки

Отдельный механизм повторяющихся **расходов** на сервисы (стриминг, облако, членства). Не путать с [периодическими операциями](ui-navigation.md) (зарплата, алименты и т.п.).

## Модель

- Таблица `subscriptions`: имя, комментарий (`description`), иконка, сайт, сумма, счёт, период (`week` / `two_weeks` / `month` / `quarter` / `half_year` / `year`), расписание, `next_run_at`, `upcoming_run_ats`, `active`.
- **`upcoming_run_ats`** — JSON-массив ровно из **трёх** ближайших дат списания (UTC). Источник правды для очереди; пользователь может править даты в форме (время — общее `time_local`).
- **`next_run_at`** — денормализованный курсор для планировщика, уведомлений и сводки; всегда равен `upcoming_run_ats[0]`.
- По умолчанию три даты заполняются последовательно из периода (`schedule.NextRunAt`). После автосписания очередь сдвигается влево, новая третья дата дописывается по интервалу между оставшимися (кейс «каждые 28 дней») или, если интервал невалиден, снова по периоду.
- Иконка — из общего каталога категорий ([categories-and-icons.md](categories-and-icons.md)); для подписок есть бренд-логотипы (Яндекс Плюс, Netflix, Spotify, Telegram, Т-Банк, Сбер, ВТБ, …). По умолчанию в форме — `subscription`.
- Системная категория **«Подписки»** (`is_system`, иконка `subscription`). Публичный CRUD подкатегорий для неё запрещён (403). Если одноимённая пользовательская категория уже есть — она переименовывается в **«Подписки (старые)»** (при коллизии имени — с суффиксом `2`, `3`…), затем создаётся новая системная.
- Подкатегория с именем подписки создаётся **лениво** (при первом списании или при привязке операций), по точному `name`. Несколько подписок с одним именем делят одну подкатегорию; различаются комментарием.
- Операции: `category_id` = «Подписки», `subcategory_id`, `subscription_id`, `description` из комментария подписки (если у операции описание пустое).

## API

Префикс `/api/v1/subscriptions` — см. [OpenAPI](api/openapi.yaml): список, summary, CRUD, `preview-upcoming`, `candidate-transactions`, `attach-transactions`, `from-recurring/{id}`.

## UI

- Web: `/subscriptions` — сводка «в месяц / в год», ближайшие списания (дата без года: «4 мая в 09:22»), CRUD (inline) с тремя редактируемыми датами и кнопкой сброса по периоду.
- Android: список `/subscriptions`; создание `/subscriptions/new`, редактирование `/subscriptions/[id]/edit` (`FormPageShell`, `leaveForm`); те же три даты.
- `/subscriptions/{id}/find-transactions` — поиск и ручной выбор операций для привязки (пресеты «автосовпадения» / «все», фильтры, score). Обычный поиск после attach остаётся на странице; переход в редактирование — только с `?next=edit` (сценарий конвертации из периодической).
- Журнал: «Сделать подпиской», «Прикрепить к подписке».
- Периодические: «Сделать подпиской» → поиск с `?mode=auto&next=edit`, затем после attach — форма редактирования. `time_local` копируется как есть (`00:00` сохраняется); пустое → дефолт `08:00`.

## Уведомления

`trigger_subscription` + `subscription_days_before` (0–30, по умолчанию 1). Шаблон `subscription_charge`. Опираются на `next_run_at` (= первая дата из JSON).

## Scheduler

Минутный runner создаёт расходные операции по `next_run_at`, затем обновляет JSON-очередь и выставляет `next_run_at` в новую первую дату.

## Плановый остаток

Ещё не списанные активные подписки с прогонами в текущем календарном месяце (TZ пользователя) входят в `forecast_balance` на дашборде и карточках счетов — вместе с операциями `kind=future` и активными [периодическими операциями](ui-navigation.md). Для подписок учитываются даты из `upcoming_run_ats` (и продолжение очереди при необходимости). UI подписывает строку по флагам `has_planned_this_month` / `has_subscriptions_this_month` («С учётом плановых», «С учётом подписок» или «С учётом плановых и подписок») — см. [transactions-display.md](transactions-display.md). После `ApplyDue` сумма уже в текущем балансе, `next_run_at` уходит вперёд — двойного учёта нет.
